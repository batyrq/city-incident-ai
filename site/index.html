Incident detectionFire, smoke, flood, crash

Detecting incidents, not counting people. Four approaches compared on real labelled images, then checked on real video. Rows in green are the default the pipeline uses.

Test sets are built from open labelled data, de-duplicated against training with a perceptual hash: D-Fire (fire, smoke), justjuu CCTV accident frames (crash), zinnia82 street-level floods (flood), with negatives from MOT17, the demo clips and 52 Mixkit clips of hard cases (sunsets, brake lights, neon, steam, rain, rivers, ambulances). Split by source clip, so no clip is in two splits.

No training: A open-vocabulary detector, B CLIP zero-shot, D ready-made community weights from Hugging Face. Trained by me: C, 4 epochs in 45.7 minutes on the Mac GPU (time-boxed to 45 min; mAP50 on the D-Fire holdout 0.57) for fire and smoke, and a linear probe on frozen CLIP embeddings (seconds) for flood and crash. Thresholds are chosen on a validation split; the test split is only used to report.

Error analysisFive ways it fails

Each case is a concrete example chosen by a rule, with the measured number. The explanations are hypotheses unless a number says otherwise.

A

Small / far people (< 50 px): 0 % recall at 640

0/254 → 2/254people under 50 px found, 640 → 960
640960

50–100 px: 6.9% → 15.1% · latency p50 37.7 → 124.5 ms

Why (hypothesis) at 640 a 1920x1080 frame is shrunk 3x, so a 40 px person becomes ~13 px, below what the stride-8 head can resolve; 960 only shrinks 2x.

Fix tiled inference (SAHI-style: run the detector on overlapping crops at native resolution and merge with NMS). Expected cost: one extra detector pass per tile, so latency grows roughly with the tile count — not benchmarked here; the measured reference point is that a single 960 pass already costs 3.3x the 640 pass and still finds only 2 of 254 tiny people. Fine-tuning on small-person data (e.g. CrowdHuman/VisDrone-style) is the other option; cost = labelled data and training time, not measured.

B

Heavy occlusion (visibility < 0.3) in a crowd

3.7%recall when visibility < 0.3 (> 0.7: 64.8%)

worst eval frame: 1 of 28 heavily occluded people found

Why (hypothesis) a person that is mostly hidden behind others produces a low objectness score and, after NMS at IoU 0.5, overlapping boxes in a dense group suppress each other.

Fix (1) feed the tracker low-confidence boxes — done, measured: recall below 0.3 visibility 3.4 % → 5.2 %, MOTA 29.9 → 35.7, at the price of +815 false positives and +26 ID switches (tracking_conf_ablation.json); (2) a crowd-trained detector or a head/upper-body detector (CrowdHuman-style fine-tune; cost = training, not measured). Even with (1), 94.8 % of < 0.3-visibility persons are still missed.

C

An ID switch from the ByteTrack evaluation

GT 11: T38 → T71130 ID switches in total, this one at frame 285

visibility at the switch 0.08 · overlap with another person IoU 0.63 · 52 frames tracked before, 63 after

Why (hypothesis) the person walked behind another pedestrian (visibility 0.08, IoU 0.63 with them), the detector lost them, and ByteTrack's Kalman prediction no longer matched when they re-emerged, so a new track was started.

Fix longer track memory. track_buffer 60 instead of 30 gave 157 vs 156 ID switches (no gain, tracking_conf_ablation.json), and BoT-SORT with ReID off gave 129 vs 130 (tracking.json), so neither motion-only change helps. Next: appearance re-identification (ReID embeddings in BoT-SORT). Expected cost: an embedding network pass per box; not measured. The tracker itself costs 1.2 ms/frame (ByteTrack) vs 10.0 ms (BoT-SORT) in tracking_timing.json, so any ReID budget is on top of that.

D

The rainy-night Times Square clip (mixkit-4332): flicker, class flips, umbrellas

96 of 193track IDs live under 15 frames (clip 4332, 596 frames)

only 5 tracks change class · 271 umbrella boxes in 60 sampled frames (not in the class filter)

Why (hypothesis) rain, glare and motion blur lower confidence around the 0.35 display threshold, so a person drops in and out of the displayed set; umbrellas hide heads and shoulders, which shifts the box and weakens appearance cues.

Fix (1) report/alert only on tracks older than N frames (zero model cost; adds an N-frame delay to events); (2) smooth the class per track by majority vote (zero cost); (3) a night/rain fine-tune. (3) cost = labelled data, not measured. None of (1)/(2) is implemented yet.

E

The IoU `collision_candidate` rule: overlapping boxes ≠ collision

26 frameswith vehicle boxes at IoU ≥ 0.35 in clip 4332 (clip 61: 2); none inspected was a collision

rule is off in the default demo config

Why (hypothesis) box overlap in a 2D, perspective view mixes depth ordering with proximity: a car behind another overlaps in the image without touching, and detector artifacts add more overlaps.

Fix require the pair to persist for several frames and a sudden change in relative velocity, class-aware duplicate suppression across vehicle classes, and ideally ground-plane positions (a per-camera homography). Expected cost: per-camera calibration for the homography; the frame-persistence and velocity checks are free at inference. No event-level ground truth exists yet to measure precision/recall of any of this.

Debugging storiesTwo bugs worth telling

INT8 gave AP50 = 0.000

The YOLO output is one tensor mixing box coordinates in pixels (0–640) with class scores (0–1). Quantizing the whole graph gave that tensor a single INT8 scale sized for the pixels, so every class score rounded to zero: max class score 0.000, 1 distinct value. The boxes still looked fine, which hid it.

Keeping the detection-head decode in FP32 restored it: max score 0.803 (FP32: 0.818), AP50 0.549 vs 0.550.

ByteTrack never saw its second pass

ByteTrack's key idea is a second matching round on low-confidence boxes. The pipeline filtered detections at conf 0.35 before tracking, above the tracker's own thresholds, so that round had nothing to match. Splitting one threshold into two (tracker input 0.1, display and events 0.35) fixed it: MOTA 5.8 points higher, measured above.

Next stepFrom city cameras to running gait

The same video-in, structured-data-out pipeline carries over to gait analysis. The pose overlay below is the first piece.

  • Pose keypoints. A pose model replaces the box: hips, knees and ankles per frame become the signal, and a runner-specific model can be fine-tuned on running footage.
  • Single-person tracking. The tracker would follow one runner and keep the identity through brief occlusions, which is the case the ablation above showed matters.
  • Step events. Foot strike and toe-off can be detected from ankle keypoint trajectories, the same way this pipeline turns tracks into events.
  • Timing evaluation. Event timing would be scored against ground truth (e.g. force-plate or manually labelled strikes), which is the evaluation this project does not yet have for its own event rules.

Honest limitationsWhat this does not do

  • Tracked objects are COCO classes only (pretrained YOLO11). Fire, smoke, flood and crash come from separate image classifiers; the crash one reacts to dashcam/CCTV style and is not reliable (see Incident detection).
  • Small and occluded people are mostly missed: 0 of 254 people under 50 px found at 640, and 3.7% recall at visibility under 0.3.
  • The event rules are pixel-threshold heuristics with no event-level ground truth, so their precision and recall are unmeasured.
  • The old 2D box-IoU collision rule is off and kept only as a legacy option; the learned crash detector replaces it.
  • Evaluation covers three MOT17 sequences (person only, 435 frames for the speed benchmark) with py-motmetrics, not the official TrackEval/HOTA; the demo clips have no ground truth. Speed numbers are single runs on one machine.
